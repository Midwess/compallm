# Documentation

Product documentation lives in the [Compallm Wiki](https://github.com/Midwess/compallm/wiki), stored in the separate Git repository `https://github.com/Midwess/compallm.wiki.git`. Before planning or making changes, read the relevant feature's architecture page and focused sub-feature pages in full from a freshly fetched Wiki checkout outside this application repository. Use `Home.md` and `_Sidebar.md` to discover the actual page filenames; do not guess page names or rely on a previous session's summary. Read the root README for project commands and the relevant Wiki pages for business rules. If Wiki access fails, report that limitation rather than inventing requirements or recreating local documentation.

When a task is discussion or documentation only, do not implement the discussed integrations or refactors. Keep unresolved business rules explicit. If an authorized change affects an architectural decision, update the relevant ADR with the change.

Docs first also includes recording the final agreed decision in the related GitHub issue: summarize the chosen behavior, scope, and acceptance criteria, and link the published Wiki pages or commit. When an issue is already established, publish that note before implementation. If no issue exists yet, retain the decision with the work and record it when the issue is created or linked, before PR creation; this does not reintroduce an issue requirement for starting work. Reuse existing issue links, preserve others' content, and avoid duplicate notes. Follow the Writing skill for concise decision summaries and verification.

Follow documentation first for new features and changes to behavior or architecture. Complete and publish the relevant Wiki documentation before changing application code, migrations, or configuration. For drafting, revising, or reviewing documentation, read and apply the [Writing skill](../skills/writing/SKILL.md), including when a general documentation skill is invoked. Write product documentation in the Wiki, not in this repository or the superseded `wiki-compallm` repository. Do not recreate a local `docs/` tree or documentation website. Organize Wiki pages directly by feature: the feature's architecture page owns decisions and open questions, and named focused pages own each flow and its configuration. For example, `Provider.md` owns provider decisions and `Provider-management.md` owns management behavior. Maintain `Home.md` and `_Sidebar.md` when adding or renaming pages. Keep shared engineering instructions in `AGENTS.md`. Do not create development or data-privacy sections, central ADR groupings, or a central business-decisions page. ADRs describe the latest architecture and solution directly: responsibilities, data flow, contracts, constraints, and relevant operational guidance. State briefly when a solution is planned rather than implemented, and keep unresolved requirements explicit. A documentation-only request does not authorize implementation afterward.

Write documentation only about the current architecture and direct solution. Describe the latest decision in place; do not retain decision dates, timelines, superseded alternatives, review history, implementation diaries, or PR/branch narratives. Do not document visual interface design, screen layouts, colors, spacing, typography, mockups, design references, or canvas-editing workflows. Keep application behavior, component architecture, security, API contracts, and necessary setup/operational instructions when they explain the solution. Apply this rule when creating or revising any documentation, including ADRs; it takes precedence over conflicting historical/status templates in writing skills. Visual specifications belong in design assets and component code, not documentation.

Every feature ADR must take less than six minutes to read, including diagrams and tables. Apply the estimate and editing checks in the [Writing skill](../skills/writing/SKILL.md). Estimate prose at 200 words per minute and allow at least 30 seconds per diagram; aim for 500–800 words or fewer. The six-minute ceiling is a project decision, not a rule attributed to the handbook.

Use the $writing skill when writing code comment, document, wiki, technical doc.
